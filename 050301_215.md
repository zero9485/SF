## Coding Execution Playbook

### 1) Pre-change checks
- Load the available docs, task context, and existing records before coding.
- Mirror the request exactly; do not reinterpret requirements or add extras.
- When the workspace is remote, read and write via `ssh` / `scp`; assume local tools do not see that tree.
- If the environment provides a layout file: read it once, then follow only paths it names; do not pair that read with reads of guessed paths.

### 2) Change strategy
- Keep the patch minimal and localized to the requested target.
- Reuse patterns from nearby code that already works before inventing a new approach.
- Protect existing correct behavior while applying the fix.

### 3) Tooling style
- Favor a single chained terminal command when steps are sequential.
- Read the full file first, then edit.

### 4) Validation and handoff
- Run relevant checks and treat results as the source of truth.
- Re-verify the modified target after each meaningful change.
- Be careful with boundary checks.
- Commit what you've changed.
- Communicate briefly and clearly.
- When a persistent notes area exists, leave a short generalized takeaway.

### 5) Learning principles
- **Evidence over intuition:** prefer observed outcomes over confidence.
- **Short feedback loops:** many small cycles beat one large speculative pass.
- **Explicit memory:** write down lessons so they transfer to future runs.
- **Error as signal:** failures are training data, not dead ends.
- **Generalization over overfitting:** optimize for recurring patterns, not one-off wins.

### 6) Git discipline
- Branch before editing using the branch name the ticket specifies; if another task branch already exists, branch from that newest branch, not from default.
- Set `git config user.name` and `user.email` before the first commit (missing identity can block commits quietly).
- Stage explicit paths only (`git add path/to/file`); avoid bulk `git add -A`.
- Use one-line commit messages; do not amend, rebase, or squash unless the ticket or policy explicitly allows it.
- Add a sensible `.gitignore` early once when needed (e.g. `__pycache__/`, `*.pyc`, `.pytest_cache/`).

### 7) Durable notes (`/workspace/learned/`)
- When `/workspace/learned/` exists, treat it as shared memory across runs: short factual notes, not long narratives.
- **`repo.md`** — Layout paths, test command, branch rules — one fact per line.
- **`bugs.md`** — Each line: failing test or symptom → cause → fix shape; verified fixes only.
- **`tooling.md`** — Environment quirks and the workaround that worked.
- Write immediately when something surprises you; edit lines in place (no duplicates); replace a line when observation contradicts it.
- Skip facts `git log` could re-derive (generic language tips, today’s SHA, ephemeral paths).
