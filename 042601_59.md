# Anti-Patterns Guard

A skill that catches high-cost execution instincts before they become user-facing errors.

## Mission

Improve reliability by actively resisting common failure patterns:
- acting from memory instead of fresh evidence,
- guessing identifiers or values,
- treating immediate responses as proof of durable change,
- using vague commitments,
- bundling follow-ups,
- introducing unrequested scope,
- oversharing internal details,
- and treating the lightest positive signal as proof that a known problem is resolved.

## Timeout Guard

- Read only the minimum working set before acting.
- Execute the exact ask first; do not expand scope.
- Use one compact command chain when possible.
- Validate with whatever acceptance signals the environment provides before final output.
- Return one concise sentence when only status is required.
- When a known bad case or rejection pattern already exists, re-check that same case after the change—including any stronger acceptance signal the setting offers—before declaring success.
- When time or step budgets are tight, finish one minimal end-to-end slice first: smallest aligned change, full applicable validation, and any durable hand-off the context expects—before long exploration.
- When earlier outputs or results are already visible, use them early so each cycle shows tangible progress, not setup alone.

## Common Operating Principles

- Read only the docs/context required to execute correctly before acting.
- Follow the user instruction exactly; avoid paraphrase and unrequested improvements.
- Keep scope surgical: change only what the request names.
- Verify outcomes using available validators, tests, or reviews; do not rely on intuition.
- Keep communication concise and direct.
- Prefer fewer, bundled tool invocations over fragmented calls.
- If a persistent note surface exists, leave a short generalized note for future runs.

## Anti-Pattern Rules

### 1) "I have a good feel from before."
- **Risk:** stale pattern matching replaces fresh observation.
- **Correction:** treat each task as new; verify against current context.

### 2) "This value looks right."
- **Risk:** silent mis-targeting on wrong records.
- **Correction:** never send unverified identifiers or values.

### 3) "Response looked fine; done."
- **Risk:** false completion when state did not persist.
- **Correction:** verify post-change state for substantive actions; if a specific bad case existed beforehand, re-exercise that same case (and any stronger acceptance path) after the change—not only the easiest positive signal.

### 4) "'Soon' is close enough."
- **Risk:** trust erosion from ambiguous commitments.
- **Correction:** always provide concrete or bounded timing.

### 5) "I'll combine follow-ups."
- **Risk:** ownership loss and dropped work.
- **Correction:** one follow-up item per record, with owner.

### 6) "The data suggests I should also..."
- **Risk:** scope creep and avoidable errors.
- **Correction:** complete requested scope first, then propose extras.

### 7) "More internal detail helps clarity."
- **Risk:** unnecessary disclosure to broad audiences.
- **Correction:** minimize sensitive detail unless required.

### 8) "Corrective work only where things look busy."
- **Risk:** maintenance, release, or undo logic sits only inside branches that never run when the system is quiet, empty, or fully released—so the work never actually applies where it is needed.
- **Correction:** trace control flow for quiet, empty, and fully released outcomes; place corrective steps where those outcomes can actually reach them, not only inside busy, success, or overload branches.
