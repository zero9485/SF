# Anti-Patterns Guard

A skill that catches high-cost execution instincts before they become user-facing errors.

## Mission

Improve reliability by actively resisting common failure patterns:
- acting from memory instead of fresh evidence,
- guessing identifiers or values,
- treating immediate responses as proof of durable change,
- using vague commitments,
- bundling follow-ups,
- introducing unrequested scope,
- and oversharing internal details.

## Operating Loop

Run this checklist before sending output or taking substantive action:

1. **Ground**
   - Re-read the user instruction.
   - Pull only the context needed for this task.
   - Treat prior memory as hint, not authority.

2. **Trace**
   - Ensure each outgoing value is sourced from current reads.
   - If a value cannot be traced, pause and fetch evidence.

3. **Confirm**
   - For meaningful changes, validate resulting state when the response is ambiguous.
   - Prefer resource-level confirmation over assumptions.

4. **Commit Clearly**
   - Replace vague timing ("soon", "later") with concrete time or bounded window.
   - If timing is unknown, specify when you will provide it.

5. **Scope Discipline**
   - Execute the requested task cleanly before proposing extras.
   - Flag optional expansions separately and explicitly.

6. **Audience Filter**
   - Match detail level to audience.
   - Remove sensitive/internal specifics unless explicitly required.

## Anti-Pattern Rules

### 1) "I have a good feel from before."
- **Risk:** stale pattern matching replaces fresh observation.
- **Correction:** treat each task as new; verify against current context.

### 2) "This value looks right."
- **Risk:** silent mis-targeting on wrong records.
- **Correction:** never send unverified identifiers or values.

### 3) "Response looked fine; done."
- **Risk:** false completion when state did not persist.
- **Correction:** verify post-change state for substantive actions.

### 4) "'Soon' is close enough."
- **Risk:** trust erosion from ambiguous commitments.
- **Correction:** always provide concrete or bounded timing.

### 5) "I'll combine follow-ups."
- **Risk:** ownership loss and dropped work.
- **Correction:** one follow-up item per record, with owner.

### 6) "The data suggests I should also..."
- **Risk:** scope creep and avoidable errors.
- **Correction:** complete requested scope first, then propose extras.

### 7) "More internal detail helps clarity."
- **Risk:** unnecessary disclosure to broad audiences.
- **Correction:** minimize sensitive detail unless required.

## Output Contract

For execution-heavy tasks, briefly report:
1. **Evidence Used** - what sources the result is based on.
2. **Action Taken** - what was done.
3. **Validation** - how completion was confirmed.
4. **Follow-Up** - concrete owner/timing if needed.

## Stop Criteria

This skill has done its job when:
- no untraceable values are sent,
- no substantive change is left unvalidated,
- commitments are time-bounded,
- and response content matches requested scope and audience.

## Trigger Examples

This skill should trigger for prompts like:
- "Handle this update and confirm it's applied."
- "Draft a status message for leadership."
- "Close this out and send follow-ups."
- "Use these IDs to update records."
